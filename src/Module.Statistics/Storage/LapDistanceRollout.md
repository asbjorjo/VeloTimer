# Statistics Lap distance rollout

## Stage 1: additive storage and legacy baseline

`20261118121122_statistics_lap_distance_storage` leaves all item modes Fixed (0). Old writers still work: the database supplies Fixed when `distance_mode` is omitted, and the new entry and sample columns are nullable. Install this schema before deploying binaries that map those columns. No Facilities database access is needed. `course_layout_id` is evidence from Facilities, not a local foreign key.

The transactional migration uses the exact legacy item name `Lap` (as used by Bootstrap and Hall of Fame). If any of its entries need a snapshot, there must be exactly one definition with a finite positive configured distance. Existing foreign keys ensure entries have an item; a renamed item cannot be identified as an old Lap by geometry or distance. Resolve missing/renamed definitions or ambiguous names with operators before cutover; do not relabel records blindly. No Lap entries needing a snapshot means no stage-1 backfill, including on an empty database. No profile, validity, facility or moderation predicate is used. Only rows with a null snapshot are updated, and only their distance and (for positive persisted durations) speed. The `real` configured value is promoted to `double precision` without decimal rounding. PostgreSQL `EXTRACT(EPOCH FROM interval)` includes whole days and fractional seconds; the app stores finite Npgsql `TimeSpan` intervals with no calendar months. An affected noncanonical interval aborts rather than guessing. Nonpositive durations retain their speed.

DDL and the backfill commit together. PostgreSQL holds its ALTER TABLE locks through the update: plan a low-traffic window and allow for write-ahead log, row/index rewrites (including the speed index), replication lag and blocked readers/writers; check legacy definitions and affected row counts first. Stage-1 Down drops the new columns and cannot restore previously stored speeds. Prefer rolling back to the old binaries while leaving the additive schema installed.

## Stage 2: final backfill and activation

`20261118125831_statistics_lap_distance_activation` is a distinct, transactional Statistics migration. Its EF `Up` locks `statistics.statistics_item` and then `statistics.statistics_entry` in `SHARE ROW EXCLUSIVE` mode, reuses the frozen stage-one SQL to backfill null snapshots, validates the target, then updates only that Lap row to `distance_mode = 1` and `distance = 0`. Definition and configuration IDs, duration limits, entries, identity and moderation state are preserved. A missing Lap definition is a fresh-install no-op; the updated Bootstrap seed creates Lap directly in CourseLayout mode. The 250m pursuit item remains Fixed and unchanged.

The migration requires exactly one item named Lap, a Fixed finite positive legacy distance, at least one unique Simple same-point loop config with nonzero coursepoint IDs, no non-Simple config for Lap, no Multi config using a Lap config as its parent, and every Lap entry has a positive finite snapshot. Failure aborts the transaction, including the final sweep and activation. The migration Down deliberately raises an error: replacing the legacy distance with the zero sentinel is not safely reversible.

### Supported deployment procedure for existing installations

The Statistics migration worker runs Database.MigrateAsync() for all pending migrations. The main Helm chart creates its migration Job as a pre-install,pre-upgrade hook before application workloads. Thus a normal Helm upgrade runs any pending Statistics migrations—including both existing migration IDs when both are pending—before it updates the processor Deployment. No separate staged release, migration bypass, special values, or PostgreSQL role/session setting is used.

1. Confirm the release is ready for the integrated Facilities evidence producer, evidence-persisting Sample writer, Statistics readers/writers, UI and Bootstrap. Check the Lap definition, configured legacy distance, configuration shape, expected catch-up/backfill counts, database recovery readiness and blocked transactions. Ensure the release values specify the intended nonzero processor replica count. The migration uses only the Statistics database; it does not query Facilities. Resolve a missing/renamed/ambiguous Lap definition or unsupported configuration with operators; do not rename, relabel or delete rows to force activation.

2. Before the upgrade, have the administrator scale the deployed Statistics processor Deployment to zero. The chart subchart is named module-statistics-processor; its Deployment normally follows the Helm release name plus that subchart name (subject to Helm fullname naming). Find the actual Deployment in the release namespace using the app.kubernetes.io/instance and app.kubernetes.io/name=module-statistics-processor labels, then scale that Deployment to zero. For example, with RELEASE and NAMESPACE replaced by the deployed values:

    kubectl get deployments --namespace NAMESPACE --selector app.kubernetes.io/instance=RELEASE,app.kubernetes.io/name=module-statistics-processor
    kubectl scale deployment/ACTUAL-DEPLOYMENT-NAME --replicas=0 --namespace NAMESPACE
    kubectl wait --for=delete pod --namespace NAMESPACE --selector app.kubernetes.io/instance=RELEASE,app.kubernetes.io/name=module-statistics-processor --timeout=5m

Wait until all matching pods have terminated. This is a temporary live scale operation: do not save zero in the release values.

3. Run the normal planned Helm upgrade with the intended nonzero module-statistics-processor.replicaCount in the release values. The chart's ordinary Statistics pre-upgrade migration hook applies pending migrations transactionally; the activation migration performs the final catch-up/backfill and validation before setting the Lap item to CourseLayout. The chart's processor Deployment uses replicaCount for its desired replicas (default 1), so the upgrade restores the intended nonzero count using the upgraded image after the hook succeeds. Do not disable the migration or use special migration values.

4. Verify the Statistics migration hook completed successfully and inspect ef.__ef_migrations_history, the Lap item/configuration and all Lap entries; every entry must have a positive finite distance_metres. Verify the upgraded Statistics processor Deployment has the intended nonzero replicas and all its pods are Ready, and verify the upgraded Facilities service(s) that provide layout evidence are Ready. Then observe incoming evidence-backed results.

If migration validation or the Helm upgrade fails, leave the Statistics processor at zero. Do not scale up or restart the old processor against a partially upgraded release or activated item. The activation migration is transactional, so a migration failure rolls back its final sweep and activation; inspect the reported prerequisite/lock failure and retry the normal upgrade only after resolving it. If the hook succeeded but a later upgrade step failed, check migration history and coordinate a compatible recovery/retry before restarting any processor.

Samples already in flight before the evidence-producing upgrade may lack CourseLayoutId or closed-loop distance evidence. The migration can backfill legacy Statistics entries from the configured fixed distance, but cannot recreate missing sample evidence; those attempts must not be assigned an invented fallback and may remain unresolved unless authoritative evidence can be recovered.

For an empty fresh install, the activation migration sees no Lap and is a no-op. The updated Bootstrap worker then seeds Lap in CourseLayout mode with the zero sentinel and its loop config; it does not change the Fixed 250m pursuit seed. The Bootstrap worker must run after the schema migrations as usual.

### Data and provider notes

PostgreSQL holds both table locks through validation, backfill, activation and the EF migration-history update. Schedule a maintenance window, allow for lock waits, WAL and replication lag, and do not treat SQLite as proof of PostgreSQL behavior. The final sweep uses the same legacy policy as stage one: exact Lap name, actual configured distance, no profile/validity/facility/moderation filters, update null snapshots only, recompute speed only for positive durations, preserve existing snapshots and nonpositive-duration speeds. PostgreSQL interval epoch conversion includes days and fractional seconds; unsupported calendar-month intervals abort. Keep the original configured baseline and a recovery plan before activation because the zero sentinel and subsequent layout snapshots cannot be mapped back to one fixed distance.
